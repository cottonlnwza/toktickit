# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver the Requester-facing TokTickIT MVP so a Development Requester can create a ticket, manage permitted attachments, find owned tickets, and view ticket details through a consistent Zen Green responsive interface.

## 2. Stakeholder Request Interpretation

The IT department needs a professional requester workflow before real authentication exists. Lab 2 will use a temporary Development Requester selector as a testing context only, then enforce requester ownership across ticket creation, listing, detail access, and attachment lifecycle behavior.

## 3. Scope

### Included

- Development Requester selection for testing context.
- Create Ticket workflow with validation and backend-generated Ticket Number.
- My Tickets workflow with requester-owned search, filters, sorting, and pagination.
- Requester Ticket Detail in read-only view mode.
- Attachment upload, metadata display, active download, and soft removal.
- PostgreSQL and Prisma models for Development Requester, Ticket, Attachment, Category, and Related System.
- REST APIs, frontend screens, automated tests, E2E test, Zen Green UI, responsive behavior, and evidence documents.

### Excluded

- Real authentication, logout, passwords, password hashing, sessions, tokens, authenticated identities, and role-based authorization.
- IT Staff dashboard, queues, claiming, assignment, IT priority changes, and ticket-owner functions.
- Public Comments, Internal Notes, Actions Taken, and collaboration/work-tracking features.
- Ticket lifecycle changes after initial `New` status.
- Administrator functions and reference-data management screens.

## 4. Functional Requirements

- FR-01: The system shall provide a Development Requester Selection screen before requester-owned screens are used.
- FR-02: The system shall load only active Development Requesters in the selector.
- FR-03: The system shall show the selected Requester identity in the application shell.
- FR-04: The system shall allow changing the selected Requester and reloading requester-specific data.
- FR-05: The system shall allow a selected Requester to create a Ticket.
- FR-06: The system shall generate the official Ticket Number on the backend.
- FR-07: The system shall set every newly created Ticket to initial Current Status `New`.
- FR-08: The system shall load active Categories and Related Systems from the database.
- FR-09: The system shall validate required fields on both frontend and backend.
- FR-10: The system shall validate attachment type, size, and active attachment count.
- FR-11: The system shall preserve entered Create Ticket form values after safe API failure.
- FR-12: The system shall prevent duplicate submission while a Ticket create request is processing.
- FR-13: The system shall show a selected Requester's own Tickets in My Tickets.
- FR-14: The system shall support search, filtering, sorting, secondary sorting, and pagination for My Tickets.
- FR-15: The system shall show loading, empty, no-results, and failure states for requester-owned lists.
- FR-16: The system shall allow opening an owned Ticket Detail screen.
- FR-17: The system shall reject direct access to Tickets owned by another Requester.
- FR-18: The system shall display Ticket Detail fields as read-only requester information.
- FR-19: The system shall allow adding permitted Attachments to an owned Ticket.
- FR-20: The system shall allow downloading active Attachments owned through the selected Requester.
- FR-21: The system shall allow soft-removing an owned Attachment with confirmation and reason.
- FR-22: The system shall retain removed Attachment metadata while blocking preview and download.
- FR-23: The system shall provide responsive desktop, tablet, and mobile layouts.
- FR-24: The system shall provide accessible labels, visible focus, keyboard access, and non-color indicators.
- FR-25: The system shall keep reviewer and AI-use evidence documents updated from real events only.
- FR-26: The system shall store the selected Development Requester in browser local storage for Lab 2 testing continuity.
- FR-27: The system shall use a two-step attachment workflow: create Ticket first, then upload Attachments with multipart requests linked to that Ticket.

## 5. Business Rules

- BR-01: The official Ticket Number is generated by the backend and must be unique.
- BR-02: A new Ticket begins with Current Status `New`.
- BR-03: Lab 2 uses a Development Requester selector for testing only; it is not authentication.
- BR-04: Inactive Development Requesters must not appear in the selector.
- BR-05: A Ticket belongs to exactly one Development Requester.
- BR-06: A selected Requester may view only their own Tickets and Attachments.
- BR-07: Category and Related System choices must come from database reference data.
- BR-08: Summary and Description are required and must be trimmed before validation and persistence.
- BR-09: Duplicate create submissions must be blocked while the first request is processing.
- BR-10: Safe error messages must not expose stack traces, SQL, secrets, or internal implementation details.
- BR-11: Allowed Attachment types are JPG/JPEG, PNG, WEBP, and PDF.
- BR-12: Attachment maximum size is 5 MB per file.
- BR-13: A Ticket may have at most five active Attachments.
- BR-14: Attachment removal must be soft removal.
- BR-15: Removed Attachments remain visible as metadata but cannot be previewed or downloaded.
- BR-16: My Tickets query behavior must always apply selected Requester ownership before search, filters, sorting, or pagination.
- BR-17: Empty list state means the selected Requester has no Tickets; no-results state means filters/search hide all matches.
- BR-18: Documentation evidence must describe real review, AI, test, and implementation events only.
- BR-19: Stored Ticket status value is `NEW`; requester-facing display text is `New`.
- BR-20: Requested Priority business urgency order is `URGENT > HIGH > MEDIUM > LOW`. Ascending priority sort returns `LOW`, `MEDIUM`, `HIGH`, `URGENT`; descending priority sort returns `URGENT`, `HIGH`, `MEDIUM`, `LOW`.
- BR-21: The selected Requester is stored as `toktickit.devRequesterId` in browser local storage and must be revalidated against active Requesters on app load.
- BR-22: If the stored Requester is missing, inactive, deleted, or cannot be loaded, the app clears the stored value and returns to the selector.
- BR-23: Changing Requester clears requester-owned screen data and reloads data for the new Requester.
- BR-24: Ticket creation and Attachment upload use a two-step workflow; if Attachment upload fails after Ticket creation, the Ticket remains created and the UI shows retry/remove guidance for failed Attachments.
- BR-25: Attachment stored filenames must be generated by the server and must not trust user-provided names for storage paths.
- BR-26: Removal reason is required for soft-removing an Attachment.

## 6. UI Specification Summary

The UI uses the Zen Green design language defined in `ui-spec.md`. It includes an application shell with TokTickIT identity, active navigation, Requester identity display, and Change Requester action. Create Ticket uses a form layout with read-only/system-generated fields visually distinct from editable fields. My Tickets uses desktop table and mobile-friendly representation. Ticket Detail is read-only for ticket fields and separates Attachment actions from ticket information. All screens must include loading, validation, success, failure, empty/no-results where applicable, and responsive behavior for desktop `>= 992px`, tablet `768-991px`, and mobile `< 768px`.

## 7. Data Changes

The implementation will extend the existing Prisma schema while preserving the Lab 1 `Category` model and its seed behavior.

### Prisma Models

| Model | Fields | Relationships |
|---|---|---|
| `RequesterUser` | `id Int @id @default(autoincrement())`, `name String`, `email String @unique`, `isActive Boolean @default(true)`, `createdAt DateTime @default(now())`, `updatedAt DateTime @updatedAt` | One Requester owns many Tickets |
| `Category` | Existing Lab 1 fields: `id`, `name @unique`, `createdAt`; add `isActive Boolean @default(true)` only if approved in Issue #17 | One Category is used by many Tickets |
| `RelatedSystem` | `id Int @id @default(autoincrement())`, `name String @unique`, `isActive Boolean @default(true)`, `createdAt`, `updatedAt` | One Related System is used by many Tickets |
| `Ticket` | `id`, `ticketNumber String @unique`, `requesterId`, `categoryId`, `relatedSystemId`, `summary`, `description`, `requestedPriority`, `currentStatus`, `createdAt`, `updatedAt` | Belongs to one Requester, Category, and Related System; has many Attachments |
| `Attachment` | `id`, `ticketId`, `originalFilename`, `storedFilename`, `mimeType`, `sizeBytes`, `storagePath`, `uploadedAt`, `removedAt`, `removedByRequesterId`, `removalReason` | Belongs to one Ticket; removal actor references Requester |

### Enums

| Enum | Values | Rationale |
|---|---|---|
| `RequestedPriority` | `LOW`, `MEDIUM`, `HIGH`, `URGENT` | Fixed ordering supports sort and badges |
| `TicketStatus` | `NEW` | Storage value remains stable while UI displays `New` |

- Create Lab 2 migration after failing database tests are in place.
- Do not delete or rewrite the existing Lab 1 migration.
- Preserve existing Category rows and extend only through additive migration where needed.
- Use PostgreSQL-compatible Prisma schema and generated client.

### Required Idempotent Seed Data

- Categories: Account and Access, Hardware, Software, Network.
- Related Systems: Email, Campus Wi-Fi, VPN, LEB2 App, Grade Submission App, Printer, Corporate Laptop.
- Development Requesters: at least four active realistic Requesters and one inactive Requester.

## 8. API Contract

Detailed API behavior is defined in `api-spec.md`. Required capabilities include retrieving active Categories, Related Systems, and Development Requesters; creating a Ticket; retrieving selected Requester Tickets; retrieving one owned Ticket; uploading Attachment; retrieving Attachment metadata; downloading active Attachment; and soft-removing Attachment. Every endpoint must define success response, validation failure, ownership failure, missing-resource behavior, safe unexpected-error behavior, and status code.

## 11. Assumptions and Decisions

- Ticket Number format: Decision: `TTK-YYYYMMDD-####`, generated by backend from Ticket creation date plus daily sequence. Rationale: readable, date-traceable, and unique with a sequence.
- Summary limit: Decision: required, trimmed, 5-120 characters. Rationale: short enough for lists and long enough for a useful title.
- Description limit: Decision: required, trimmed, 20-2000 characters. Rationale: encourages useful detail without excessive storage/UI burden.
- Requested Priority values and sort order: Decision: business urgency order is `URGENT > HIGH > MEDIUM > LOW`; ascending sort is `LOW` -> `MEDIUM` -> `HIGH` -> `URGENT`; descending sort is `URGENT` -> `HIGH` -> `MEDIUM` -> `LOW`. Rationale: simple requester-facing urgency scale with deterministic sorting.
- Status storage/display: Decision: store `NEW`, display `New`. Rationale: stable enum storage with readable UI text.
- Searchable fields: Decision: Ticket Number, Summary, Category name, Related System name. Rationale: covers likely requester lookup behavior.
- Filterable fields: Decision: Category, Related System, Requested Priority, Current Status. Rationale: aligns with visible classification fields.
- Sortable fields: Decision: createdAt, updatedAt, requestedPriority, ticketNumber. Rationale: supports recency, priority, and official number ordering.
- Default sorting: Decision: newest updatedAt first, secondary ticketNumber descending. Rationale: newest activity appears first with stable tie-breaker.
- Page numbering: Decision: one-based `page`; permitted page sizes `5`, `10`, `20`; default `10`. Rationale: predictable UI-friendly pagination.
- Invalid query behavior: Decision: return HTTP 400 with safe field-specific query error. Rationale: invalid controls should be visible and testable.
- Attachment storage strategy: Decision: store files under `server/uploads/lab-02/` and keep DB metadata. Rationale: keeps uploaded files out of client assets and links files to DB records.
- Safe filename strategy: Decision: generate stored filename from UUID plus validated extension; retain original filename as metadata. Rationale: avoids trusting user filenames.
- Upload/creation failure behavior: Decision: two-step workflow creates Ticket first, then uploads Attachments. If an upload fails, the Ticket remains and the UI shows failed Attachment state with retry/remove guidance. Rationale: avoids losing valid Ticket data because supporting evidence failed.
- Ownership failure response: Decision: return HTTP 404 for unauthorized Ticket/Attachment access. Rationale: avoids confirming another Requester's resource exists.
- Safe error disclosure: Decision: client receives stable messages without stack traces, SQL, filesystem paths, secrets, or tokens. Rationale: protects implementation details.
- Zen Green tokens and component rules: Decision: use required Lab Sheet colors plus semantic tokens in `ui-spec.md`. Rationale: keeps UI consistent and auditable.
- USER CONFIRMATION REQUIRED: `docs/lab-02/reviewer.md` currently includes student identity details based on Lab 1 convention. User must confirm this is acceptable for Lab 2 repository documentation before commit.
